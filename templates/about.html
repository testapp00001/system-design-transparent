About this project

Plenty of developers spend years building CRUD apps with MVC, a single database and a manual deploy. Nothing wrong with that — but it means the things senior backend interviews (and real scale) ask about are only learned by people lucky enough to work somewhere that already does them.

Retries and idempotency keys. Why MySQL and PostgreSQL store rows differently and what that does to performance. Connection pools. Replication and failover. Background jobs. Blue-green deploys. How Discord moved trillions of messages from Cassandra to ScyllaDB. These ideas are scattered across conference talks, company blogs and social-media clips — if you happen to see them.

System Design Transparent writes that knowledge down in one place, for free, in the open.

How it works

  • Articles are Markdown files in the GitHub repository. Anyone can fix, extend or add one with a pull request, so the content can be kept up to date instead of going stale.
  • The roadmap lists every topic we think a backend engineer should at least know exists, including ones nobody has written about yet.
  • Vote rounds decide what gets written next. A round opens for a few tags (say database, networking, system-design) for a few days. Anyone can suggest a topic and vote — no account needed.
  • Accounts are optional: just a username and password, used to save, like and upvote articles. No email, no tracking.

This site is also a worked example

The code behind this site uses, in miniature, several of the patterns the articles explain. It is small enough to read in an afternoon:

  • PostgreSQL full-text search with weighted tsvectors, GIN indexes and trigram typo tolerance — src/posts.rs
  • Race-free vote limits with transaction-scoped advisory locks — src/votes.rs
  • Idempotent "set state" endpoints instead of toggles — set_reaction
  • A background job that runs on every instance but does its work exactly once — src/worker.rs
  • Server-side sessions with hashed tokens, Argon2id passwords, CSRF protection via Fetch Metadata — src/auth.rs, src/security.rs
  • Trusting X-Forwarded-For correctly and grouping IPv6 by /64 — src/ip.rs
  • Graceful shutdown, health checks, a multi-stage Dockerfile and a CI pipeline — see the repository

Contributing

Read CONTRIBUTING.md for the article template and style guide. Good articles explain the problem first, then the mechanism, then the trade-offs, and say clearly when not to use something. Accuracy beats length: link to primary sources (official docs, the company's own engineering blog) for every claim about a real system.
